## Problem Statement

MTDO is a solo-built, actively-dogfooded terminal app (kanban + Pomodoro + Learning Coach +
AI assistant + Practice Lab, config-driven curriculum) that the founder now wants to open
to more users than just himself. Every future AI-assisted coding session on this repo risks
scope-creeping the product back toward "just another generic dashboard" unless the project's
non-negotiable boundaries are stated explicitly, in a place a fresh agent (or contributor)
actually reads before making changes.

The user supplied a fully-formed 7-part briefing template for this purpose: one-sentence
core loop, anti-goals before goals (MTDO's: no video/animation panel ever, no mouse
dependency, no hardcoded curriculum), an explicit data/code boundary, panels described by
the decision they help the user make (not by widget), tech constraints with the reason
attached, a failure-mode contract for when the "smart" (AI) part is unavailable, and build
order as independently-shippable slices. The full verbatim template, with MTDO-specific
content already filled in by the user, is in the Appendix below — this is what actually
gets appended to `CLAUDE.md`.

## Constraints

- Must respect the repo's existing convention: `CLAUDE.md` is a short, single-purpose file

## Approaches Considered

### Approach A: In-place `CLAUDE.md` extension
Append all 7 sections directly into the existing `CLAUDE.md`, after the current
bug-linking-convention section.
- Effort: S (human: ~15 min / CC: ~5 min) — Risk: Low
- Pros: zero new files, one read gets everything, no indirection.
- Cons: reverses `CLAUDE.md`'s own established thin-pointer convention (22 lines today,
  explicitly delegates deep content elsewhere); will keep growing as MTDO adds panels/screens
  and stop being a fast first-read.
- Completeness: 6/10

### Approach B: New versioned `docs/agent-contract.md` + one-line pointer (Codex's proposal, Claude's recommendation)
Write the full contract to a new `docs/agent-contract.md`; `CLAUDE.md` gets one new line
pointing to it — the same pattern it already uses for `.claude/PROGRESS.md`.
- Effort: M (human: ~30-45 min to review/tune wording / CC: ~10 min) — Risk: Low
- Pros: matches the repo's existing "pointer, not payload" convention exactly; fully
  portable — a new contributor gets it on `git clone` with zero machine-local setup; room to
  grow without bloating the first-read file.
- Cons: one more file to keep in sync if the architecture changes; slightly more indirection
  for someone who wants only the 30-second version.
- Completeness: 9/10

### Approach C: Split — non-negotiables inline, expandable detail in `docs/`
Core loop, anti-goals, data/code boundary, and failure contract go directly in
`CLAUDE.md`; screens-by-decision and build-order rationale go into `docs/agent-contract.md`,
linked from `CLAUDE.md`.
- Effort: M (human: ~30 min / CC: ~10-15 min) — Risk: Medium (two files, drift risk)
- Pros: the rules an agent most needs on its first read are unmissable, not one hop away;
  keeps fast-growing detail out of the first-read file.
- Cons: two places a future editor can forget to update; the "stable vs. growing" split
  boundary is a judgment call that can get relitigated.
- Completeness: 7/10

## Appendix: Verbatim Template to Append to `CLAUDE.md`

The user's original wording, MTDO-specific content already filled in — this is the content
Approach A appends after the existing "Linking a commit/branch to a tracker bug" section:

> **Core loop:** A user opens a terminal, sees today's study/practice tasks, works one task
> in a focused view that shows live coaching for that exact task, and closes the session
> having practiced something real (code that ran, not just a checked box).
>
> **Anti-goals (never add, even if it seems natural):**
> - No video/animation panel, ever — every panel exists to help the user learn and retain,
>   not to entertain.
> - No mouse dependency — keyboard-driven, for users who already live in a terminal.
> - No hardcoded curriculum — content is config, not code, or the app gets forked every time
>   the user's goals change.
>
> **Data/code boundary:** curriculum and categories live in a user-edited config file, never
> in application logic. The app is a generic engine over a config schema.
>
> **Screens, by decision not widget:**
> - Kanban board — what am I studying right now?
> - Pomodoro/streaks — am I actually showing up consistently?
> - Learning Coach panel — for the active task, what should I focus on and what mistakes do
>   people make here (real coaching, not "study X")? Can generate a DSA/SQL problem on
>   demand.
> - AI assistant panel — task context is already loaded; no re-explaining yourself.
> - Practice Lab — did the code I just wrote actually run, against a real database?
>
> **Tech + reason:** Terminal UI (Textual/Python), because the target user already lives in a
> terminal and switching to a browser is the friction being removed.
>
> **Failure contract:** if the AI backend isn't configured or errors, fall back to static
> content — never block the core loop on an external call.
>
> **Build order (historical — already shipped, this is why it was sequenced this way):**
> 1. Kanban + config loading — usable day one, no AI required.
> 2. Pomodoro/streaks — retention loop.
> 3. Coaching panel — static content first, AI-generated as fallback-fill later; MVP never
>    required AI wiring.
> 4. Practice Lab / real code execution — highest technical risk, built last.
> 5. Profiles/multi-user — only once single-user worked end to end. (Still incremental —
>    CLI-only today, no in-app switcher yet.)
